# Internationalization Rules

- Use `@nuxtjs/i18n`; do not add another i18n library.
- Keep English (`en`) as the source locale and `prefix_except_default` as the URL strategy.
- Author messages in TypeScript under `i18n/locales/<locale>/`, one semantic namespace per file.
- Register each namespace explicitly in the locale `index.ts`; do not use `import.meta.glob` or a
  second message-loading mechanism.
- Keep namespace export keys equal to their filenames and identical across locales.
- Use lowercase semantic namespace names and `camelCase` message keys. Name keys by meaning, not by
  English wording or UI position.
- Put generic reusable labels in `common`; keep domain copy in its domain namespace.
- Route all user-facing application copy through `$t` or `useI18n().t`; do not hardcode display text
  in templates, components, or composables.
- Use `$t` directly in templates. In `<script setup>`, call `useI18n()` once and destructure `t`.
- Use named interpolation and pluralization; do not concatenate translated sentences or put logic,
  HTML, or provider data in translations.
- Keep translation keys explicit. For finite status or error sets, use a typed map rather than
  constructing keys dynamically.
- Map stable provider/API error codes to translation keys at the app boundary. Logs, identifiers,
  diagnostics, and provider-owned content are not translation messages.
- Resolve localized content during SSR. Add locale alternates only when matching content exists in
  more than one locale.
- Follow `.ai/skills/implement-i18n/SKILL.md` when adding copy, namespaces, or locales.
