# Internationalization Rules

## Standard

- Use the `@nuxtjs/i18n` module. Do not add another i18n library.
- Default locale is English (`en`); it is currently the only locale.
- URL strategy `prefix_except_default`: the default locale has no path prefix, other locales are
  prefixed (e.g. `/de/...`). Adding a language must not change the default-locale URLs.
- Messages are authored in **TypeScript**, one feature namespace per file, aggregated by a per-locale
  `index.ts`. Register a single aggregator per locale (`file: 'en/index.ts'`).

## File layout

```text
i18n/locales/
└── en/
    ├── index.ts        # aggregator: imports every namespace, exports the merged map
    ├── common.ts       # namespace: generic reusable labels
    ├── dashboard.ts    # namespace: dashboard feature
    └── ...
```

- Each namespace file default-exports one plain serializable message object. Use nested objects for
  meaningful groups such as `actions`, `status`, or `errors`; do not repeat the namespace inside the
  file.
- `index.ts` imports them and exports `{ common, dashboard, ... }`. The object keys are the
  namespaces, so keys read as `t('common.appName')`, `t('dashboard.title')`.
- The aggregator (not the file name) provides the namespace; keep each export key equal to its file
  name.
- Register namespaces **explicitly** in `index.ts` (one `import` + one entry in the exported map). Do
  **not** auto-collect with `import.meta.glob` — globbing makes the merged type `unknown` and loses
  typed `t()` keys.

## Authoring copy

- All user-facing text goes through i18n (`$t` / `useI18n().t`). Never hardcode display strings in
  templates, components, or composables.
- English is the source of truth: every key exists under `i18n/locales/en/` first.
- Do not put logic, HTML, or provider data in translation values. Use vue-i18n interpolation and
  pluralization for variables and counts instead of string concatenation.
- In templates, call `$t` directly. In `<script setup>`, call `useI18n()` once and destructure `t`.
  Do not call `useI18n()` at module scope or wrap it in a second project-specific translation helper.
- Keep provider/API error codes stable and map them to i18n keys at the app boundary. Server logs,
  technical diagnostics, identifiers, and provider-owned content are not translation messages.
- Avoid constructing keys dynamically. When a finite status or error set needs mapping, use an
  explicit typed map so missing cases are visible in review and typecheck.

## Usage pattern

```vue
<template>
  <button type="button">{{ $t('common.actions.save') }}</button>
  <p>{{ $t('notification.items', itemCount) }}</p>
</template>

<script setup lang="ts">
const { t } = useI18n()

const title = computed(() => t('dashboard.welcome', { name: displayName.value }))
</script>
```

```ts
// i18n/locales/en/common.ts
export default {
  actions: {
    save: 'Save',
    cancel: 'Cancel',
  },
}
```

```ts
// i18n/locales/en/notification.ts
export default {
  items: 'no notifications | 1 notification | {count} notifications',
}
```

## Naming

- Namespace / file: a domain/feature, **lowercase, single word** where possible: `common`,
  `dashboard`, `profile`, `auth`, `search`, `validation`, `error`. Generic reusable labels (save,
  cancel, close, loading, retry) live in `common`.
- Keys: `camelCase`; object nesting creates dot-separated paths (`dashboard.welcome`,
  `common.actions.save`).
- Name by **meaning, not the English text**: `notification.empty`, not
  `notification.youHaveNoNotifications` — copy can change without renaming the key.
- No abbreviations, no UI-position names (`topButton`), no sentences as keys.
- Variables via named interpolation: `welcome: 'Welcome, {name}'` →
  `t('dashboard.welcome', { name })`.
- Counts via pluralization: `items: 'no items | 1 item | {count} items'` →
  `t('notification.items', count)`.
- Keys are identical across every locale.

## Adding a namespace

1. Create `i18n/locales/en/<namespace>.ts` exporting its message object.
2. Import it in `i18n/locales/en/index.ts` and add it to the exported map — **no `nuxt.config.ts`
   change needed**.
3. Replicate the file for every other locale.

## Adding a language

1. Register the locale in the i18n config (`code`, `language`, `file`).
2. Copy the whole `i18n/locales/en/` folder to `i18n/locales/<code>/`, translate the values, keep keys
   and file names identical.
3. Handle `hreflang`/alternates only through the module; keep canonical URLs correct.

## Type safety

Because messages are TypeScript, `t()` keys can be typed from the English schema: augment `vue-i18n`'s
`DefineLocaleMessage` with `typeof` the English aggregator so keys autocomplete and missing/renamed
keys fail typecheck. Add this once at project level when enabled; do not create per-feature
augmentations or competing message schemas.

## SSR and SEO

- Resolve the locale before render; localized content must be in the server-rendered HTML.
- Enable locale alternates/`hreflang` only once more than one locale exists.
